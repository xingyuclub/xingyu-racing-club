# 星屿积分截图识别去重与身份绑定设计

## 目标

解决截图识别中同一张图片被识别、计分多次，以及识别到的后台队员无法稳定对应已有积分人物的问题。此次只处理这两项，页面刷新回到顶部另行处理。

## 业务规则

1. 去重以原始截图内容为第一依据，不以“同一成员出现”或“人员+名次相同”作为同图证据。
2. 完全相同的图片在同一批次只保留第一次出现，后续图片标记为自动重复并不调用 AI、不产生积分。
3. 视觉高度相似但无法证明完全相同的图片不得静默丢弃，必须进入“疑似重复图片”人工确认；确认不同后两场都保留，确认重复后跳过后者。
4. 识别出的昵称必须先匹配当前 `roster` 队员。
5. 每个当前队员必须绑定一个现有 `scoreMembers` 积分人物，且绑定唯一；没有绑定、绑定失效或绑定冲突时，批次不可提交。
6. 识别提交不得自动创建新的积分人物。新积分人物只能通过后台积分人物管理或明确的数据导入流程产生。
7. 既有 `scoreMembers` 中名称变体（例如带/不带中点）不自动合并；只允许管理员显式选择绑定目标，避免历史积分被静默并账。

## 方案

### 原图去重

上传后为每张图片生成文件 SHA-256，并在识别前生成一个统一方向、统一尺寸、灰度像素的规范化指纹。规范化指纹用于识别同图的不同压缩/文件容器版本。完全匹配自动去重；近似匹配只生成阻塞性疑似重复问题，保留人工确认入口。

重复图片不会发送给 AI。批次中保留原图索引、`duplicateOfImageIndex` 和判定来源，前端显示“已跳过重复图片”或“疑似重复图片”。

### 身份绑定

在 `roster` 成员上保存 `scoreMemberId`。配置归一化时仅对“标准化姓名唯一匹配”的情况自动补齐；无法唯一匹配的成员保持未绑定。配置校验拒绝不存在的积分人物 ID 和重复绑定。

识别草稿匹配到 roster 后读取该成员的 `scoreMemberId`。缺失或无效时产生 `unlinked-score-member` 问题并阻止提交；草稿和提交流程均不再调用 `createScoreMemberId` 或追加 `scoreMembers`。

审核界面继续允许修正“对应成员”，但只展示已绑定且有效的候选；未绑定成员提示先到队员管理完成绑定。提交前服务端再次按当前配置重建草稿并执行同样校验。

## 数据流与兼容

旧批次没有图片指纹时，在重新处理/重新匹配时按当前原图补算。旧批次中已经自动创建的积分人物不自动删除或合并；新的识别不会继续制造此类身份。配置迁移保留所有原字段，新增字段默认为空。

## 验收标准

- 同一张截图重复上传两次，AI 只调用一次，草稿只产生一场，后者显示自动重复。
- 同一比赛布局但内容不同的两张截图不会因相同成员和名次被自动丢弃。
- 近似但不确定的图片显示阻塞性疑似重复，未确认前 `canCommit=false`。
- roster 成员没有有效 `scoreMemberId` 时，识别预览显示绑定异常且提交按钮不可用。
- 绑定到现有积分人物后，提交只写入该 ID，`scoreMembers` 数量不增加。
- 不存在的积分人物 ID、重复绑定和旧配置不完整字段均有服务端测试覆盖。
