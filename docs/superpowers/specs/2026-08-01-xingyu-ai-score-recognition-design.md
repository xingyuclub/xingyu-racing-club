# 星屿积分截图识别与自动联动设计

## 状态

- 设计已由用户分段确认
- 本文只定义第一版范围、数据规则和验收标准，不包含实现代码
- 目标：管理员上传比赛截图并确认识别结果后，自动更新星屿积分榜

## 1. 目标与边界

第一版在现有配置后台的积分编辑器中增加截图识别、周末录入和识别记录功能。管理员选择日期并上传 JPG、JPEG 或 PNG 截图；服务端调用 OpenAI 图片理解接口提取比赛和名次，使用本地确定性规则完成成员匹配、去重、计分和局数限制。所有结果必须经过批量预览确认，确认后才写入积分并立即刷新公开 H5。

第一版同时提供一次性历史迁移工具，将旧 Excel 的 `S53-kw27` 至 `S53-KW31` 转换为新积分模型。

第一版不包含：

- 公开 H5 上传入口
- 周六、周日截图自动识别
- 自动修改桌面的旧周表文件
- 自动新增车队成员
- 高置信度结果自动提交
- 已录入局次的直接覆盖
- 本地 OCR 备用链路

## 2. 术语与唯一数据来源

### 当前成员

运行时配置 `roster` 是当前车队成员的唯一来源：

- ID 存在于最新 `roster` 的成员是当前成员。
- 后台新增成员后，该成员立即进入识别匹配范围和公开排行榜。
- 后台删除成员后，该成员立即退出识别匹配范围、公开阵容和公开排行榜。
- Excel、截图和历史记录中的昵称不能自动创建当前成员。

比赛积分和别名都使用成员 ID 关联。昵称只用于识别和展示。识别记录同时保存当时的昵称快照；成员以后被删除时，历史比赛仍然保留并标记为历史成员。

历史 Excel 中无法匹配当前成员的昵称使用独立历史参与者 ID，并登记在后台专用的历史参与者表中。历史参与者 ID 永远不会因为昵称相似而自动并入当前 `roster`；只有管理员在导入预览中明确选择当前成员时才建立成员关联。

识别开始时记录成员名单版本，提交前重新读取配置并校验版本。期间发生新增、删除、改名或别名变化时，阻止提交并要求重新确认匹配。

### 比赛类型

比赛标题中包含“排位赛”时归类为排位赛；其他标题全部归类为队内赛。批量预览允许管理员修改识别出的类型。

## 3. 后台信息架构

在现有积分编辑器增加三个标签页：

1. `截图识别`
2. `周末录入`
3. `识别记录`

现有在线积分编辑、Excel 模板下载、导入预览和数据导出继续保留。

### 截图识别

批次级日期默认为当天，管理员必须在识别前确认日期。同一批次日期固定，但可混合队内赛和排位赛截图。每批不设置硬性张数上限，界面提示建议不超过 20 张。

支持四类主要版式：

- 排位赛最近比赛列表
- 个人竞速赛最近比赛列表
- 单场个人比赛结算详情
- 单场组队比赛结算详情

列表截图中每个比赛标题对应一场比赛，按截图从上到下拆分；不同图片之间按上传顺序处理。同一场比赛只上传列表或详情中的一种，不要求两张图联合识别。

### 批量预览

预览必须同时展示原图和结构化结果，并允许完整编辑：

- 比赛类型
- 比赛局次/处理顺序
- 截图日期和时间
- 玩家昵称
- 游戏显示名次
- 当前成员匹配
- 是否非车队成员
- 新增或删除参赛者行
- 最终计算积分

无法匹配当前 `roster` 的昵称默认标记为非车队成员，管理员可改选为当前成员。确认映射时可以选择“记住此别名”；别名只能由管理员显式保存、修改或删除，不能因一次人工匹配自动落盘。

任何日期冲突、昵称待确认、名次缺失、接口失败或结构校验失败都会阻止整批提交。

## 4. AI 职责与确定性校验

OpenAI 只提取截图事实：

- 截图中显示的日期和时间
- 比赛标题
- 比赛在截图中的顺序
- 所有参赛者昵称
- 游戏显示名次

OpenAI 不负责判断当前成员、计算积分、去重、分配局次或决定是否提交。上述业务逻辑全部由服务端确定性代码执行。

API Key 只从服务端 `.env` 的 `OPENAI_API_KEY` 读取，模型名称从 `OPENAI_VISION_MODEL` 读取。浏览器不接触 API Key。图片由本机 Express 服务端发送给 OpenAI。

## 5. 计分规则

### 队内赛

所有实际参赛者都计入人数，包括非车队成员；只为当前车队成员保存积分。

```text
得分 = max(min(实际参赛人数, 6) - 游戏显示名次 + 1, 0)
```

示例：4 人赛依次得到 `4、3、2、1` 分。超过 6 人时封顶 6 分，第 7 名及以后为 0 分。非车队成员仍参与人数和名次计算，但其分数不写入车队积分。

### 排位赛

游戏机制允许每场最多 3 名车队成员。非车队成员不占车队积分名额。

1. 从截图参赛者中筛出当前车队成员。
2. 按游戏显示名次从前到后排列这些成员。
3. 按车队成员相对名次计分。

```text
1 名车队成员：1
2 名车队成员：2、1
3 名车队成员：3、2、1
```

示例：游戏名次包含 `2、4、6`，只有第 4、6 名是当前车队成员，则第 4 名得到 2 分，第 6 名得到 1 分。

### 每人独立局数限制

局数限制作用于“成员 + 日期 + 比赛类型”，不是整场比赛：

- 每名成员每天队内赛最多 3 局。
- 每名成员每天排位赛最多 3 局。
- 系统按图片上传顺序、图片内从上到下顺序，给每名成员写入第一个空局。
- 同一场中某成员已经录满 3 局时，只跳过该成员；其他未满成员继续录入。
- 同一成员同一类型超过 3 局时，只保留其最先处理的 3 局，其余在预览中标记为未录入。
- 已保存的局次禁止由识别流程覆盖；管理员必须先在现有积分编辑器中清空旧数据。

## 6. 去重规则

重复判断使用比赛内容，不只使用文件字节。以下条件全部相同视为同一场：

- 日期
- 比赛类型
- 实际参赛人数
- 标准化后的参赛昵称集合
- 每个昵称对应的游戏显示名次

同一文件重新截图、缩放、压缩或裁剪后，只要比赛内容一致仍应识别为重复。重复比赛不占成员的 3 局名额；系统继续处理后续上传图片。

文件哈希同时保留，用于快速识别完全相同的上传文件。

## 7. 提交与实时联动

提交采用全批次原子写入：

1. 重新读取最新配置和成员名单版本。
2. 重新运行全部校验、去重和计分。
3. 生成当前配置备份。
4. 写入临时文件。
5. 成功后替换正式配置并将批次标记为已提交。

任一步失败都保持原积分不变。

保存成功后，服务端发送配置更新事件，已打开的公开 H5 立即重新请求 `/api/config`。现有的首次加载、窗口重新获得焦点和 `cache: 'no-store'` 逻辑继续作为断线兜底。

## 8. 识别记录与原图

每批永久保存在本机：

- 原始截图
- 文件哈希
- AI 原始结构化输出
- 人工修改后的结果
- 成员匹配快照
- 去重和跳过原因
- 最终写入积分
- 状态、创建时间和提交时间

批次状态：

```text
已上传 -> 识别中 -> 待确认 -> 已提交
                  -> 识别失败
```

任意图片调用失败时整批标记为识别失败，不写入积分；原图保留，管理员可以重试。

识别记录页支持按日期、比赛类型和状态筛选，并查看原图、原始识别结果、人工修改结果和最终积分。识别记录页只负责审计，不提供覆盖积分的入口。

## 9. 周六、周日手动数据

周六、周日不进入截图自动识别流程。周末录入页默认列出当前全部车队成员，未参赛成员可留空。

每名成员每天保存三个可编辑字段：

- `积分`
- `得分`
- `总分`

三个字段原样保存，不由系统重算。周末 `总分` 是该日期截至当时的权威累计值：计算时间线到达该周末记录时，运行累计值直接替换为 `总分`，之后的工作日比赛积分继续在该值上累加。成员没有周末总分时沿用此前累计积分。

## 10. 历史 Excel 迁移

历史迁移只读取：

| 工作表 | 日期范围 |
|---|---|
| `S53-kw27` | 2026-06-29 至 2026-07-05 |
| `S53-kw28` | 2026-07-06 至 2026-07-12 |
| `S53-KW29` | 2026-07-13 至 2026-07-19 |
| `S53-KW30` | 2026-07-20 至 2026-07-26 |
| `S53-KW31` | 2026-07-27 至 2026-08-02 |

忽略 `S52`、`队内赛`、`离队` 和 `群成员`。

迁移规则：

- 周一至周五读取每人的队内赛 3 局和排位赛/开黑赛 3 局。
- 成员当天 6 局全部为 0 时仍生成完整记录。
- 周六、周日原样读取 `积分 / 得分 / 总分`。
- 最新周末 `总分` 在对应日期替换此前累计值，不再重复累加同一周末数据；后续工作日积分继续从该值累加。
- 标准化昵称和别名用于匹配当前成员。
- 无法匹配当前 `roster` 的昵称保存为历史成员，不进入当前公开阵容和排行榜。
- 导入前展示所有解析数据、成员映射和异常项。
- 确认后完整覆盖 2026-06-29 至 2026-08-02 的现有积分记录，范围外数据不变。
- 导入前生成完整配置备份；任一校验失败都不执行覆盖。

后台数据成为唯一来源。后续可以随时导出新的标准化积分 Excel，但不自动修改桌面的旧周表文件。

## 11. 建议数据边界

运行时公开配置继续只包含前台需要的数据。识别原图、AI 原始输出、历史审计元数据和 API 配置不得进入公开 `/api/config`。

建议新增独立持久化边界：

```text
server/
  data/
    site-config.json                 # 当前公开业务配置来源
    historical-score-members.json   # 不属于当前 roster 的历史参与者
    score-recognition-index.json     # 批次索引和审计元数据
  storage/
    score-recognition/<batch-id>/    # 原图和识别结果
```

具体文件写入沿用现有配置存储的备份、临时文件和原子替换方式。当前成员仍只读取 `site-config.json` 中最新 `roster`。

## 12. 安全与权限

- 所有识别、重试、提交、周末录入和历史导入接口沿用现有后台登录认证。
- 公开 H5 不提供上传入口。
- 仅接受 JPG、JPEG 和 PNG，并校验扩展名、MIME 类型和图片解码结果。
- 客户端文件名不得直接用于存储路径。
- API Key、原图路径和 AI 原始输出不进入前端公开配置。
- 该功能继续只适合本机或受信任局域网，不得作为公网后台部署。

## 13. 验收标准

### 计分

- 队内赛 4 人正确得到 `4、3、2、1`。
- 队内赛包含非车队成员时，非车队成员参与人数计算但不写入积分。
- 排位赛 2 名车队成员正确得到 `2、1`。
- 排位赛 3 名车队成员正确得到 `3、2、1`。
- 排位赛车队成员游戏名次不连续时仍按车队相对名次计分。
- 同场部分成员满 3 局时只跳过已满成员。

### 识别与提交

- 四类主要截图能够解析为统一结构。
- 列表截图可以拆成多场并保持页面顺序。
- 重复内容不占成员局数。
- 日期冲突、AI 失败、成员待确认和名次缺失会阻止整批提交。
- 提交失败不会部分修改积分。
- 成员名单在识别期间发生变化时会阻止提交。

### 成员变化

- 后台新增成员后立即进入识别候选和公开排行榜。
- 后台删除成员后立即退出当前识别候选和公开排行榜。
- 删除成员不会删除历史比赛、截图或昵称快照。
- 成员改名后既有积分继续关联原成员 ID。

### 历史与周末

- 只迁移 KW27 至 KW31，并使用确认的日期范围。
- 工作日全零行仍被保留。
- 周末三个字段原样保存且可手动编辑。
- 周末总分在对应日期正确替换累计值，后续工作日积分继续累加。
- 非当前历史成员不会进入当前公开阵容和排行榜。

### 回归与浏览器

- `npm test` 通过。
- `npm run build` 通过。
- OpenAI 调用、结构校验、去重、计分、局数、历史迁移和原子提交具有自动化测试。
- 在 390、768、1280 视口验证上传、预览、周末录入和识别记录页面。
- 后台宽表只在自身区域横向滚动，页面无横向溢出。
- 提交后已打开的公开 H5 自动刷新积分榜，窗口聚焦刷新仍可兜底。

## 14. 已知风险

- 特殊 Unicode 昵称和游戏字体可能导致识别误差，因此人工预览是强制步骤。
- 游戏更新可能改变截图版式；AI 提取提示词和验证层必须允许新增版式样本，而不能把坐标写死。
- 原图永久保留会持续占用磁盘，需要在识别记录页显示批次文件大小，后续再评估归档功能。
- OpenAI 接口受网络、额度和模型可用性影响；第一版失败时只支持保留原图并重试，不提供本地 OCR 回退。
- 历史周表结构不完全统一，迁移必须逐表校验表头和日期映射，不能按固定绝对列号盲读。
