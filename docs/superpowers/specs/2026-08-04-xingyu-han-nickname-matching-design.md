# 星屿截图昵称汉字匹配设计

日期：2026-08-04

## 1. 目标

降低本地视觉模型对队标前缀、性别符号、标点和装饰字符识别不稳定造成的昵称未匹配，同时避免通过模糊匹配把积分写给错误成员。

本次只调整截图昵称到当前 `roster` 成员的确定性匹配规则。AI 输出、计分、去重、三局槽位、`scoreMembers` 映射和人工审核流程保持不变。

## 2. 采用方案

匹配按以下优先级执行：

1. 使用现有 `normalizeNickname` 对当前成员名称和人工别名做完整字符串精确匹配。
2. 完整匹配失败后，从截图昵称和每个当前成员名称中只提取 Unicode 汉字。
3. 截图昵称包含至少 2 个汉字，汉字序列与某个成员完全一致，并且该序列只对应一个成员时，自动匹配该成员。
4. 其他情况返回未匹配，继续进入现有人工映射或明确忽略流程。

例如：

```text
xy²·黑岩       -> 黑岩 -> ˣʸ༩·黑岩
xγ_十二        -> 十二 -> ˣʸ༩·十二
এ᭄云嗔        -> 云嗔 -> এ᭄云嗔
```

“完全一致”指提取后的汉字数量、内容和顺序全部相同。不得使用包含、子序列、编辑距离、同音字或近似字符匹配。

## 3. 安全边界

- 汉字少于 2 个时不启用汉字兜底。成员“米”只有在现有完整昵称或人工别名精确匹配时才能自动命中。
- `Q3`、`Rose`、`fafa` 等无汉字昵称继续使用完整匹配、人工别名或人工确认。
- 如果未来两个成员提取出相同汉字，汉字索引将该键标记为冲突，任何截图都不能通过该键自动匹配。
- 截图昵称多出、缺少或识别错误任意汉字时不自动匹配。例如“黑岩岩”“黑”“黑沿”都不能匹配“黑岩”。
- 人工别名的精确匹配优先于汉字兜底；本次不自动学习或写入新别名。
- 未匹配结果继续阻止提交，不能因汉字兜底而绕过现有审核门槛。

## 4. 实现边界

在 `src/data/scoreRules.js` 增加一个纯函数，用 Unicode 属性转义提取汉字：

```js
extractHanCharacters(value)
```

`buildMemberMatcher` 构建两个只读索引：

- 完整规范化昵称和别名索引，保持现有行为。
- 至少 2 个汉字的成员名称索引；重复键保存为冲突状态，而不是选择第一个或最后一个成员。

调用匹配器时先查完整索引，失败后再查唯一汉字索引。`buildScoreMemberMatcher` 不变，因为截图不会直接匹配历史积分人物。

## 5. 错误处理

汉字提取为空、只有一个汉字或命中冲突键时统一返回 `null`，由现有识别草稿生成 `unmatched` 异常。前端不新增提示类型，也不隐藏原始 OCR 昵称，用户仍可通过原图核对后映射或忽略。

## 6. 测试与验收

自动测试覆盖：

- 队标和装饰符号完全识别错误，但“黑岩”“十二”等全部汉字正确时可匹配。
- 中文与非中文混合昵称只比较汉字，例如成员 `巫溪ya` 与 OCR 结果 `x?巫溪99` 提取后都等于“巫溪”，因此可以命中。
- 多一个、少一个、错一个或顺序不同的汉字均不匹配。
- 单字昵称“米”不走汉字兜底，但完整精确昵称“米”仍可匹配。
- `Q3`、`Rose`、`fafa` 保持完整昵称和别名匹配能力。
- 两个成员汉字序列冲突时返回未匹配。
- 现有前缀、别名、草稿汇总、计分和提交测试保持通过。

真实截图验收至少抽取当前误差明显的队标符号样本，确认汉字完全正确时由未匹配转为正确成员；汉字本身识别错误的样本仍保留为待处理异常。

## 7. 非目标

- 不做模糊 OCR、同音字、繁简转换或形近字纠错。
- 不向视觉模型发送完整成员名单。
- 不自动创建或保存别名。
- 不改变一字昵称和纯英文昵称的审核策略。
- 不修改任何积分计算规则。
