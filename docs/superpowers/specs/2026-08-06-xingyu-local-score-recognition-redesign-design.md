# 星屿积分截图纯本地识别重构设计

最后更新：2026-08-06

## 1. 背景与目标

当前积分截图识别已经无法稳定支撑自动化录入，主要问题包括：

- 昵称识别和积分成员匹配不稳定，管理员仍需逐人核对。
- 相同比赛可能因截图动画、昵称前缀差异或跨批次上传而无法去重。
- 不同比赛可能因人员和名次相同而被错误合并。
- 录像与挑战等非结算页面可能被当作完整比赛计分。
- AI 数值列在相同原图的多次识别中不稳定，不适合作为自动去重依据。

本次重构目标是建立一条纯本地、可解释、保守自动化的识别管线：正常截图自动完成识别、成员匹配、去重和计分；只有真正无法确定的昵称或字段需要人工处理。

部署后继续使用本机 Ollama，不依赖 OpenAI API Key，不调用外部云端模型。

## 2. 已确认约束

- 只接受完整比赛结算排名表截图。
- 录像、挑战、最近比赛列表、加载页和其他页面不得进入积分计算。
- 一张截图只能对应一场比赛，不再支持一张截图拆分多场比赛。
- 不识别也不使用截图底部日期或截图显示时间。
- 保留并使用排名表中每位玩家的完赛时间。
- 相同地图、相同参赛人数、相同名次与完赛时间序列直接自动去重。
- 地图不同，或任一名次对应的完赛时间不同，必须视为不同比赛。
- 自动成员匹配宁可留待确认，也不得错误关联积分成员。
- 已提交积分不由本次重构自动修改。

## 3. 已验证根因

### 3.1 不同比赛被错误合并

真实批次中两张截图的人员和名次相同，但地图分别为“洛杉矶”和“彩虹风车岛”，所有玩家完赛时间也不同。当前提示词明确忽略地图和时间，并把头像附近的等级数字误识别为 MVP 分，最终生成相同的数值签名并自动合并。

结论：人员、名次和 AI 数值列不能单独作为比赛唯一身份。

### 3.2 相同比赛无法稳定去重

当前内容签名使用 AI 原始昵称。相同成员可能被识别为 `xy♂·fafa`、`.fafa` 或 `♀·fafa`，从而生成不同签名。现有图片相似度也容易受到动画、高亮和截图时刻影响，并且只在当前批次比较，无法识别历史批次已经提交的比赛。

结论：比赛身份不得依赖原始 OCR 昵称，也必须支持跨批次比较。

### 3.3 AI 数值列不稳定

现有存档中共有 32 组内容完全相同的重复原图，其中 9 组多次识别结果不一致。同一张图的数值可能从 `308/359/406` 变化为 `309/351/400`。

结论：MVP、攻击、防御、援助等 AI 数值列全部退出去重逻辑。

### 3.4 本地模型具备必要能力

使用现有 `xingyu-score-recognition` 本地模型进行只读实验时，模型能够从真实截图稳定提取：

- 页面类型；
- 地图名称；
- 玩家昵称；
- 名次；
- 每位玩家的完赛时间。

模型能够把完整结算表识别为 `result`，把“录像&挑战”页面识别为 `replay`。同一比赛的两张截图得到相同完赛时间序列，不同地图比赛得到不同地图和完赛时间序列。

## 4. 总体架构

采用“整图识别 + 确定性校验 + 异常行局部复核”的分阶段纯本地管线：

```text
上传原图
  -> 文件级历史去重
  -> 页面类型识别
  -> 整图比赛事实提取
  -> 结构与字段校验
  -> 异常昵称行裁剪复核
  -> 积分成员分层匹配
  -> 比赛身份与跨批次去重
  -> 确定性计分和局次分配
  -> 异常审核
  -> 原子提交
```

AI 只负责读取截图事实。页面放行、成员身份、比赛去重、积分计算、局次分配和是否允许提交全部由服务端确定性代码决定。

## 5. 识别数据结构

每张合格结算截图生成一个比赛事实对象：

```js
{
  screenType: 'result',
  mapName: '洛杉矶',
  participants: [
    {
      nickname: '赴约·太困',
      rank: 1,
      finishTime: '01:36:62'
    }
  ]
}
```

明确不保存到比赛事实中的字段：

- 截图底部日期或显示时间；
- 玩家等级；
- MVP 分；
- 攻击、防御、援助；
- 氮气覆盖、贴弯率、CWW 率；
- AI 推测的积分或成员身份。

## 6. 页面类型与输入限制

### 6.1 允许输入

只有同时满足以下条件的图片才能进入后续流程：

- 页面被识别为完整结算排名表；
- 存在明确地图名称；
- 存在一组排名行；
- 每个排名行包含名次、昵称和完赛时间。

### 6.2 拒绝输入

以下页面直接标记为不支持，不生成积分：

- 录像与挑战页面；
- 最近比赛列表；
- 单纯地图或房间信息页；
- 加载页、分享页和其他非完整结算页面；
- 一张图片包含多张比赛卡片的组合图。

后台必须展示拒绝原因和原图入口。拒绝单张图片不得中断同批其他合格图片的处理。

## 7. 整图提取与确定性校验

### 7.1 整图提取字段

本地模型一次只提取：

- `screenType`；
- `mapName`；
- `participants[].nickname`；
- `participants[].rank`；
- `participants[].finishTime`。

### 7.2 校验规则

- `screenType` 必须为 `result`。
- `mapName` 标准化后不能为空。
- 名次必须从 `1` 连续递增，不得缺失或重复。
- 每一名次必须恰好对应一个排名行。
- 完赛时间必须符合游戏显示格式，并且每个排名行都必须存在。
- 不允许模型返回多个比赛对象。

任何规则失败都不得计算积分。系统先尝试局部复核；复核仍失败时生成阻塞问题。

## 8. 昵称局部复核

### 8.1 触发条件

以下情况只对对应排名行进行裁剪、放大和第二次本地识别：

- 整图昵称无法匹配任何候选；
- 同时命中多个候选；
- 昵称只剩单字或明显残缺；
- 整图结果与已有高置信度别名冲突。

### 8.2 决策规则

- 整图结果和局部结果标准化后一致，可继续自动匹配。
- 两次结果不同但只有一个高置信度候选时，仍进入人工确认，不自动采用。
- 复核结果不得覆盖截图原始识别文本，两次结果均需保存在审计记录中。

局部复核只处理异常行，正常截图不会重复调用整图模型。

## 9. 积分成员匹配

### 9.1 匹配优先级

1. 当前成员名称和管理员确认过的别名；命中后转换为其永久绑定的积分成员 ID。
2. 完整积分成员名单的标准化精确匹配。
3. 唯一汉字匹配、已知车队前缀变体和受限字符相似度匹配。
4. 无唯一高置信度结果时进入人工确认。

当前成员只用于提高候选优先级，后台人工选择列表仍必须展示完整积分成员名单。

### 9.2 自动匹配原则

- 自动匹配必须唯一且达到高置信度。
- 单字昵称、相似名称、多候选和残缺名称不得自动关联。
- 最终计分身份始终使用 `scoreMemberId`，不使用 AI 原始昵称或 roster ID。

### 9.3 人工纠正积累

人工选择积分成员时提供“记住该昵称”选项。只有管理员显式确认后，标准化 OCR 昵称才保存为该积分成员的识别别名。以后出现相同 OCR 结果时可自动匹配。

未经确认的模型猜测不得写入永久别名。

### 9.4 非积分成员

确实存在于截图但不在积分成员名单中的玩家，必须由管理员明确标记为非积分成员。该行继续参与队内赛参赛人数计算，但不写入个人积分。

## 10. 比赛身份与去重

### 10.1 文件级去重

上传后首先计算原文件 SHA-256，并与以下范围比较：

- 当前批次其他图片；
- 未提交识别批次；
- 已提交识别历史。

完全相同的文件直接标记重复，不调用模型，也不占局次。

### 10.2 比赛身份键

标准比赛身份由以下字段组成：

```text
标准化地图名称
+ 参赛人数
+ 按名次排列的完赛时间序列
```

例如：

```text
洛杉矶::3::1=01:36:62|2=01:37:85|3=01:42:06
```

昵称和积分成员 ID 不进入硬去重键，避免昵称 OCR 波动导致同一比赛无法去重。

### 10.3 自动判定规则

- 比赛身份键完全一致：自动判定为同一比赛并去重。
- 地图不同：自动判定为不同比赛。
- 地图相同但任一名次完赛时间不同：自动判定为不同比赛。
- 底部截图时间、动画、高亮、截图格式和压缩差异全部忽略。

### 10.4 不确定情况

地图或任一完赛时间缺失时，不生成比赛身份键，也不使用昵称、名次集合、AI 数值列或图片相似度猜测。系统执行局部复核，仍失败则阻止该图片提交。

图片感知相似度只能用于提示可能存在重复上传或触发复核，不能自动合并比赛。

### 10.5 跨批次去重

已提交批次必须持久化比赛身份键。新批次生成身份键后，与所有历史已提交身份键比较。命中时展示原批次、原图和提交日期，并自动跳过当前比赛。

## 11. 计分与提交

- 页面类型、结构、比赛身份和成员匹配完成后，才调用现有确定性计分函数。
- 队内赛的参赛人数包含明确标记的非积分成员。
- 排位赛继续按有效积分成员的相对名次计分。
- 每人每日每类型三局限制继续使用现有槽位规则。
- 重复比赛和拒绝图片不得占用局次。
- 提交前重新读取最新配置和历史比赛身份，再执行一次完整校验和去重。
- 批次继续采用原子提交；任一阻塞问题存在时不得写入积分。

## 12. 后台审核体验

默认展示每张图片的结果状态：

- 已识别；
- 已自动去重；
- 非结算页面；
- 昵称待确认；
- 地图或完赛时间待确认；
- 已超过个人局次限制。

正常图片默认收起，只显示地图、参赛人数和本场积分摘要。异常图片默认展开，并提供：

- 原图；
- 地图；
- 名次、原始昵称、局部复核昵称和完赛时间；
- 最终积分成员；
- 去重命中的历史批次和原图；
- 明确的阻塞原因。

管理员只需处理异常项，不再逐人核对正常分数。

## 13. 历史数据与迁移

- 已提交的 `dailyScores` 和 `weekendScores` 不自动改写。
- 未提交批次可使用新管线重新识别和重建草稿。
- 历史已提交识别批次使用已保存原图重新提取比赛身份键，但只写入识别审计索引，不修改积分。
- 无法生成可靠身份键的历史批次保持原状态，并标记为“历史身份不完整”。
- 如需修正历史错误，单独输出审计清单，经管理员确认后再执行，不并入本次自动迁移。

## 14. 验证方案

### 14.1 真实截图基准集

基准集使用现有识别存档的真实截图，至少覆盖：

- 同一比赛的多张截图，包含动画和高亮差异；
- 不同地图但人员与名次相同；
- 同一地图但完赛时间不同；
- 完全相同文件的本批和跨批重复上传；
- 录像与挑战页面；
- 车队前缀变体、模糊昵称、单字昵称和非积分成员；
- 缺行、重复名次和完赛时间不可读。

每张图片记录人工确认的页面类型、地图、排名行、积分成员或非积分成员状态，以及应当对应的比赛身份。

### 14.2 验收指标

- 完整结算页识别成功率：100%。
- 非结算页面拦截率：100%。
- 完全相同文件去重率：100%。
- 相同比赛去重率：100%。
- 不同比赛错误合并数：0。
- 自动积分成员匹配错误数：0；无法确认可以进入人工审核。
- 所有最终积分均可追溯至原图、地图、名次和完赛时间。

### 14.3 新旧结果对照

上线前使用新管线只读重跑现有真实截图，输出：

- 旧识别结果；
- 新识别结果；
- 人工基准结果；
- 发生变化的页面分类、成员匹配、比赛去重和最终积分。

未达到验收指标前，不替换正式识别流程，也不写入任何积分数据。

## 15. 实施边界

本次重构只覆盖：

- 截图类型识别；
- 比赛事实提取；
- 昵称局部复核与成员匹配；
- 文件级与比赛级跨批次去重；
- 识别审核展示；
- 真实图片基准测试和历史身份索引迁移。

不包含：

- 云端模型或 OpenAI API；
- 自动修改已提交积分；
- 重新设计普通积分编辑、周末录入或公开积分榜；
- 支持非完整结算页或一图多场；
- 使用 MVP、攻击、防御、援助等字段参与去重。

## 16. 实施顺序

1. 建立真实截图基准数据和只读评估工具。
2. 收紧 AI schema，完成页面分类和单场事实提取。
3. 增加结构校验和异常行局部复核。
4. 重建分层成员匹配和显式别名学习。
5. 实现文件级、比赛级和跨批次去重索引。
6. 改造审核 UI，只突出阻塞异常。
7. 使用基准集完成新旧对照，不写入积分。
8. 指标达标并经管理员确认后，才切换正式处理流程。
