# 星屿截图识别简化设计

日期：2026-08-04

## 1. 目标

截图识别只服务一个业务结果：确认每位当前车队成员在本批截图中应增加多少积分，并将确认后的分数写入现有积分明细。

本次简化不再要求 AI 识别或保存胜负、比赛时间、地图、MVP 等与积分写入无关的信息。模型只负责读取截图中的场次边界、昵称和名次；比赛类型由用户在上传前选择，日期使用批次日期，计分、匹配、去重、三局上限和汇总全部由服务端确定性代码完成。

## 2. 核心约束

- 每个上传批次只能选择一种比赛类型：`team`（队内赛）或 `ranked`（排位赛）。
- 同一批次可以上传 1 至 20 张截图。
- AI 不计算积分，也不决定最终积分人物。
- AI 输出不包含标题、地图、日期、时间、胜负、MVP 或其他比赛属性。
- 用户看到的主视图按人物汇总，但底层继续保留逐场、逐图证据。
- 未处理的异常必须解决后才能提交；用户可以将未匹配昵称映射到当前成员，或明确标记为非车队成员并忽略。
- 现有 `scoreMembers`、`dailyScores` 三槽结构、排行榜、周末录入和 Excel 导入导出保持兼容。

## 3. 方案选择

### 方案 A：AI 直接输出人物总分

输出最短，但模型需要同时识别、算分、跨图汇总和处理三局上限。错误难以追溯，也无法可靠验证，不采用。

### 方案 B：AI 输出所有旧字段，再在前端隐藏

改动最小，但模型压力和误识别来源不变，不能解决本地模型把时间、MVP 或胜负区域误当比赛数据的问题，不采用。

### 方案 C：AI 只输出场次、昵称和名次，后端算分并汇总

保留确定性计分和逐图证据，同时显著缩短提示词与 JSON 输出。该方案能够兼容队内赛人数计分和排位赛相对计分，是本次采用的方案。

## 4. 数据契约

上传批次新增必填字段 `raceType`：

```json
{
  "date": "2026-08-03",
  "raceType": "team"
}
```

AI 对每张截图只返回：

```json
{
  "matches": [
    {
      "participants": [
        { "nickname": "十二", "rank": 2 },
        { "nickname": "黑岩", "rank": 4 }
      ]
    }
  ]
}
```

保留 `matches` 层级，因为一张最近比赛列表截图可能包含多场比赛；队内赛计分也需要知道每场实际参赛人数。批次日期和比赛类型由服务端注入，不允许模型猜测。

服务端生成的草稿保留两层数据：

- `evidence`：逐图、逐场、逐成员的昵称、名次、计算分数、匹配结果和槽位状态。
- `summary`：按积分人物汇总的本批可写入总分，以及组成该总分的证据引用。

每条证据至少包含 `imageIndex`、`matchIndex`、`nickname`、`rank`、`score`、`memberId`、`slot` 和异常状态。图片继续使用批次中已经持久化的原图，不在草稿中复制 Base64。

## 5. 识别与计分流程

1. 用户选择批次日期和比赛类型，然后上传截图。
2. 服务端按上传顺序逐张调用本地视觉模型。
3. 模型只提取场次边界、所有可见昵称和游戏显示名次。
4. 服务端使用当前 `roster` 和 `memberAliases` 匹配昵称，再按规范化姓名映射到 `scoreMembers`。
5. `team` 批次使用每场实际参赛人数和游戏名次调用现有 `scoreTeamRace`。
6. `ranked` 批次使用已匹配车队成员的游戏名次调用现有 `scoreRankedRace`。
7. 服务端执行内容去重和每人每日每类型三局槽位分配。
8. 服务端从有效证据派生人物汇总，不让前端或模型自行累计。
9. 用户修正异常后，服务端重新计算证据、槽位和汇总。
10. 用户确认提交后，继续按逐局分数写入 `dailyScores`，而不是写入一个无法追溯的汇总值。

## 6. 审核界面

### 6.1 上传区

上传区包含：

- 批次日期。
- 比赛类型二选一：队内赛 / 排位赛。
- 多图上传控件。

识别开始后，本批比赛类型锁定；若选错类型，用户应取消并重新建立批次。

### 6.2 人物汇总

主视图按人物显示：

```text
十二    +8 分    查看依据
黑岩    +5 分    查看依据
浪漫    +3 分    查看依据
```

正常人物默认收起。展开后显示每条证据：截图序号、游戏名次、计算分数和槽位状态，并提供原图查看入口。

### 6.3 异常与提醒区

以下异常自动展开并标红：

- 昵称未匹配当前成员。
- 同一场出现重复或非法名次。
- 场次没有参与者。

成员达到当天该类型三局上限时自动展开并显示黄色提醒，不视为识别错误。

未匹配昵称可以执行两种操作：

- 映射到一个当前 `roster` 成员。
- 标记为非车队成员并忽略。忽略的参与者仍保留在队内赛参赛人数中，但不写入积分。

用户修改昵称映射或名次后，必须由服务端重新计算分数和人物汇总。前端不得直接修改计算后的 `score` 或总分。

### 6.4 提交门槛

存在未处理的未匹配昵称、非法名次或场次结构错误时禁用提交。三局上限属于可解释的跳过状态，不阻止提交，但必须在人物依据中明确显示“已达上限，本条不计入”。

## 7. 错误处理

- 模型未返回合法最小 JSON 时，批次进入 `failed`，保留可读错误和原图，可重试。
- 单张图片失败时标明图片序号，不把整批永久卡在 `processing`。
- 名次重复、为空或小于 1 时作为可修正异常，不静默丢弃。
- 昵称匹配不使用不透明的自动模糊合并；现有别名和已验证的车队前缀归一化继续使用，其他情况交给用户确认。
- 提交前继续校验名单版本，避免识别后成员配置发生变化导致写错人物。

## 8. 模型压力优化

- 系统提示只描述两种截图结构和昵称/名次输出，不再要求理解无关字段。
- JSON Schema 删除 `title`、`date` 和 `time`。
- 不把完整成员名单塞入视觉提示，避免模型按候选名单猜测截图内容。
- 保持 `temperature: 0`。
- 正常方向且不超过 2048px 的截图保留原始字节，避免二次压缩使浅色文字丢失；更大图片才按比例缩小。
- 图片仍按顺序逐张处理，避免本机同时加载多张大图造成内存峰值。

## 9. 测试与验收

自动测试至少覆盖：

- 上传时缺少或传入非法 `raceType` 被拒绝。
- AI 请求和返回契约不再包含标题、日期、时间、胜负和 MVP。
- 队内赛与排位赛使用用户选择的类型计算。
- 人物汇总等于其有效证据分数之和。
- 修改昵称映射或名次后由服务端重新计算汇总。
- 未解决异常阻止提交，明确忽略的路人不阻止提交。
- 三局上限、重复截图、名单版本变化继续生效。
- 原有 Excel、周末积分和公开排行榜测试保持通过。

真实验收使用当前 15 张截图：

- 整批完成识别，不出现通用 500 或永久 `processing`。
- 每一条汇总分都能定位到具体截图和名次。
- 用户能修正错误昵称或名次，并看到汇总即时重算。
- 提交前能清楚区分已计分、已忽略和因三局上限跳过的证据。
- 经人工核对后提交，公开积分榜结果与审核汇总一致。

## 10. 非目标

- 不识别或保存胜负、比赛时间、地图、MVP、攻击、防御或援助。
- 不让 AI 直接计算或汇总积分。
- 不引入新的 OCR 服务或云端模型。
- 不修改周末积分模型、Excel 格式或公开排行榜结构。
- 不自动提交 AI 结果。
